PerformanceAnalyst - System Design & Architecture

This document describes the architecture and design of the PerformanceAnalyst project located at c:\Nikhil P\SVN\Asset\13_PerformanceAnalyst\PerformanceAnalyst. The system performs offline performance analysis by ingesting metrics from multiple sources (JMeter, InfluxDB, Apache, Tomcat, Oracle, OS) and applying aggregation, anomaly detection, correlation, and rule-based evaluation to produce human-readable findings.

1. System Overview

1.1 Purpose

PerformanceAnalyst is a Python-based analysis engine that correlates load test results with infrastructure and application metrics to identify performance anomalies and likely root causes. It operates primarily as a batch analysis pipeline over a defined time window (START_TIME, END_TIME) and produces structured output for human review.

1.2 High-level Responsibilities

  • Ingest time-series and aggregate data from:
    • JMeter aggregate/summary result files.
    • InfluxDB database (macaDB) for CPU, memory, and other system metrics.
    • Apache, Tomcat, Oracle, OS sources via specialized readers.
  • Aggregate and normalize metrics per flow (business transaction) and per server.
  • Compute derived KPIs and perform anomaly detection and correlation.
  • Apply a rule engine to detected anomalies/correlations to infer issues and recommendations.
  • Format and write analysis results to disk.

3.3 Responsibilities by Layer

  • Data Source Layer (data_sources/*)
    • Encapsulate all source-specific logic for reading raw metrics.
    • Expose neutral structures (typically pandas DataFrames or equivalent iterable structures).
  • Aggregation Layer (aggregation/*)
    • Combine metrics from multiple sources into coherent, keyed datasets:
      • flow_builder.py and server_builder.py organize metrics per flow and server.
      • aggregator.py, instance_aggregator.py, and oracle_aggregator.py perform aggregation operations (e.g., grouping, averaging, percentiles).
  • Processing Layer (processing/*)
    • jmeter_processor.py:
      • Processes JMeter aggregate/summary results into standard KPIs (latency, error rate, throughput/RPS).
    • cpu_processor.py, memory_processor.py:
      • Normalize and resample CPU/memory metrics, compute derived indicators as needed.
  • Anomaly Detection Layer (anomaly_detection/*)
    • detector.py:
      • Provides analyze_dataframe(df) and detect_anomalies_and_patterns(aggregated_data).
      • Delegates to specialized detectors:
        • anomaly_utils.detect_anomalies
        • pattern_utils.detect_patterns
        • violation_utils.detect_violations
        • correlation_utils.detect_correlations
    • Other modules encode metric constants, resolution, thresholds, and correlation logic.
  • Rule Engine Layer (rule_engine/*)
    • rule_definitions.py defines the knowledge base and conditions for issues.
    • rule_engine.py evaluates rules over detected anomalies and aggregated metrics.
    • output_formatter.py produces human-readable findings (e.g., prioritized issues and recommendations).
  • Output & Utilities (utils/*)
    • output_writer.py handles writing structured results to the filesystem.
  • Core/Config (core/*, config/*)
    • config_manager.py loads and exposes configuration (YAML + Python constants).
    • settings.py provides static thresholds and default paths.
    • monitoring_config.yaml provides data-source and metric-level configuration.

4.2 Flow & Server-Level Analysis

The anomaly detection entry point, analyze_dataframe(df) in anomaly_detection/detector.py, operates over a pandas DataFrame representing metrics for a specific entity (flow or server). 

def analyze_dataframe(df):

    results = {
        "anomalies": [],
        "patterns": [],
        "violations": [],
        "correlations": []
    }

    if df is None or df.empty:
        return results

    # APPLY DETECTORS
    detect_anomalies(df, results)
    detect_patterns(df, results)
    detect_violations(df, results)
    detect_correlations(df, results)

    return results

def detect_anomalies_and_patterns(aggregated_data):

    analysis_results = {
        "flows": {},
        "servers": {}
    }

    # FLOW LEVEL
    for flow_id, df in aggregated_data["flows"].items():
        analysis_results["flows"][flow_id] = analyze_dataframe(df)

    # SERVER LEVEL
    for server, df in aggregated_data["servers"].items():
        analysis_results["servers"][server] = analyze_dataframe(df)

    return analysis_results

The aggregated_data structure is expected to contain:

  • aggregated_data["flows"]: a mapping of flow_id → DataFrame for each business flow.
  • aggregated_data["servers"]: a mapping of server_id → DataFrame for each server or host.

Each DataFrame includes metric columns from multiple sources (e.g., CPU, memory, latency, error rates) aligned over time. The anomaly detection layer enriches the results dict, which is later consumed by the rule engine.

5.4 Tuning Strategy

  • Most threshold changes are done by editing config/settings.py.
  • For new metrics or more complex behaviour, configuration may be extended in monitoring_config.yaml and associated resolvers.
  • Thresholds are static at runtime; there is no dynamic adaptation in this design.

6. Data & Metric Model

6.1 Metric Taxonomy

Metrics are defined and organized in anomaly_detection/metric_constants.py and are resolved by metric_resolver.py. While the exact enum/list is in those files, the main categories include:

  • JMeter KPIs: latency (avg, p95, p99), error rate, RPS/throughput, response time.
  • CPU Metrics: CPU utilization per server / per core.
  • Memory Metrics: memory utilization, possibly swap usage.
  • Apache Metrics: worker utilization, request rates, error rates, response times.
  • Tomcat Metrics: GC time, GC count, heap usage, thread pool utilisation, DB connection pool usage.
  • Oracle Metrics: exec time, wait time, call count, memory usage.

6.2 Internal Data Structures

  • Aggregated Data:
    • aggregated_data["flows"]: map of flow IDs to DataFrames containing JMeter + infra metrics for each flow.
    • aggregated_data["servers"]: map of server IDs to DataFrames containing infra metrics per server.
  • Anomaly Detection Results (per flow or server):
    • results["anomalies"]: list of anomaly records (metric, time range, severity, details).
    • results["patterns"]: detected trends or patterns (e.g., steadily increasing latency).
    • results["violations"]: threshold violations and constraint breaches.
    • results["correlations"]: strong statistical correlations between metrics.
  • Rule Engine Inputs:
    • Analysis results from anomaly detection (by flow and by server).
    • Aggregated metrics (e.g., global KPI summaries from processors).

6.3 Mapping External Fields to Internal Metrics

Each reader module maps source-specific fields to internal metric identifiers defined in metric_constants.py. For example:

  • jmeter_reader.py maps JMeter result columns (e.g., avg, error%, throughput) to internal KPIs.
  • influx_reader.py maps InfluxDB measurement names/fields (e.g., cpu_usage) to CPU metrics.
  • apache_reader.py, tomcat_reader.py, oracle_reader.py perform similar mappings for their domains.

7. Anomaly Detection & Correlation Design

7.1 Anomaly Detection Workflow

  1. Input DataFrame per flow/server contains time-indexed metric columns.
  2. detect_anomalies(df, results):
    • Checks numeric metrics against thresholds (e.g., CPU > 85%, latency > 1000ms).
    • Applies duration criteria (MIN_DURATION, MIN_SUSTAINED_DURATION).
    • May incorporate trend detection (TREND_THRESHOLD).
  3. detect_patterns(df, results):
    • Identifies temporal patterns (e.g., steadily increasing metric, oscillations).
  4. detect_violations(df, results):
    • Marks constraint violations (e.g., critical latency, high error rates, GC spikes).
  5. detect_correlations(df, results):
    • Computes correlations between metric pairs using thresholds (e.g., CPU_RT_CORR_THRESHOLD).
    • Example: high positive correlation between CPU utilization and response time.

7.2 Correlation Model

  • Selects metric pairs based on configuration or hard-coded pairs (e.g., CPU vs latency, memory vs latency).
  • Computes correlation coefficients over overlapping time windows.
  • Uses thresholds like CORRELATION_THRESHOLD, CPU_RT_CORR_THRESHOLD, MEMORY_LATENCY_CORR_THRESHOLD to decide significance.
  • Correlations are recorded in results["correlations"], including metric pair, coefficient, and time range.

7.3 Multi-Level Analysis

The system deliberately analyses metrics at two logical levels:

  • Flow level: KPIs and metrics aggregated per flow (business transaction) to answer "which flows are impacted?".
  • Server level: metrics aggregated per server to answer "which nodes or tiers are the bottleneck?".

8. Rule Engine & Reporting

8.1 Rule Definitions

The rule engine resides under rule_engine/:

  • rule_definitions.py defines individual rules, each representing a performance diagnosis pattern (e.g., CPU-bound latency, DB bottleneck, GC-related slowdowns).
  • Rules typically reference:
    • One or more anomalies or violations (by metric type, severity, and duration).
    • Correlation evidence (e.g., CPU-latency correlation being high).
    • Threshold breaches (e.g., Apache worker utilization > 80%).

8.2 Rule Evaluation

  • rule_engine.py orchestrates evaluation:
    • Iterates through flows and servers.
    • Applies rules in a defined sequence or grouping.
    • Collects results as structured findings (e.g., issue type, affected flows/servers, severity).
  • Some rules may combine evidence from different tiers, for example:
    • High latency in JMeter flows + high CPU on app servers + strong correlation = CPU bottleneck diagnosis.
    • High DB wait time + high DB exec time anomalies = database contention.

8.3 Output Formatting

  • output_formatter.py maps raw rule results into user-friendly messages and sections.
  • utils/output_writer.py handles writing these formatted outputs to the output/ directory.
  • Outputs typically include:
    • Summary of detected high-level issues.
    • Per-flow and per-server findings.
    • Supporting details (metrics, anomalies, evidence, correlations).

9. Runtime View & Execution Model

9.1 Execution Model

  • The system is designed as a batch analysis pipeline:
    • The time window is defined up front (START_TIME, END_TIME).
    • All necessary data is loaded and processed for this interval.
    • Results are written to disk at the end of the run.
  • Entry-point script (not shown in excerpt) usually:
    • Initializes the configuration manager.
    • Triggers data loading in data_sources/.
    • Invokes aggregators, processors, anomaly detection, and rule engine in sequence.
    • Hands final results to output_writer.

9.4 Deployment Assumptions

  • Python environment with necessary dependencies (pandas, Influx client, etc.).
  • INFLUX_HOST is reachable and INFLUX_DB contains the relevant metrics.
  • JMeter result files are pre-generated and placed in JMeterResults/ with expected naming conventions.
  • Apache/Tomcat/Oracle/OS metrics availability depends on the configuration and readers.

10. Extensibility & Design Patterns

10.1 Patterns in Use

  • Adapter Pattern:
    • Each reader in data_sources/ adapts an external system or file format into a common internal representation.
  • Builder/Aggregator Pattern:
    • flow_builder.py and server_builder.py orchestrate which sources feed which aggregated datasets.
    • aggregator.py encapsulates aggregation logic.
  • Layered Architecture:
    • Clear separation between data ingestion, aggregation, processing, anomaly detection, and rule evaluation.

10.2 Adding a New Data Source

  1. Create a new reader module under data_sources/ that:
    • Connects to or reads from the new source.
    • Maps raw fields to internal metrics via metric_constants.py and metric_resolver.py.
    • Outputs DataFrames keyed by time and entity (flow/server).
  2. Update aggregation builders (flow_builder.py, server_builder.py) to incorporate the new metrics.
  3. Update anomaly detection (if necessary) to handle the new metrics.
  4. Optionally add new rules in rule_definitions.py that leverage the new metrics.

10.3 Adding a New Anomaly or Rule

  • Anomaly:
    • Define the new metric or pattern in metric_constants.py.
    • Extend anomaly_utils.py or pattern_utils.py to implement detection logic.
    • Update thresholds in settings.py or configuration as needed.
  • Rule:
    • Add a new rule to rule_definitions.py that composes anomalies, patterns, and correlations.
    • Ensure rule_engine.py invokes the rule and that output_formatter.py formats its output.

11. Non-functional Aspects & Limitations

11.1 Performance

  • Uses DataFrames for vectorized operations where possible (depending on implementation of readers and processors).
  • Analysis is bounded by the configured time window, which limits data volume per run.
  • Potential bottlenecks:
    • Large InfluxDB queries for long windows.
    • Computing correlations across many metric pairs.

11.2 Reliability & Error Handling

  • Defensive checks such as:
    • if df is None or df.empty: return results in analyze_dataframe.
  • Individual reader failures or missing data will typically manifest as absent metrics for specific flows/servers, rather than total pipeline failure (depending on reader implementations).

11.3 Limitations & Assumptions

  • Thresholds are static and may require manual tuning for different environments.
  • Analysis assumes JMeter results and system metrics are aligned in time and refer to the same test period.
  • No explicit real-time / streaming design; the system is intended for post-hoc analysis.
