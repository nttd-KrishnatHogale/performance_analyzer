1. Prerequisites

1.1 Software

  • Python: 3.x (3.8+ recommended)
  • Python packages (typical set, inferred from code – adjust based on your environment):
    • pandas
    • influxdb or influxdb-client (depending on influx_reader.py)
    • Any additional packages referenced by your readers or requirements.txt

Install packages, for example:

pip install pandas influxdb

Or install from your project-specific requirements.txt if available.

1.2 External Systems & Data

  • InfluxDB
    • Running instance reachable from the PerformanceAnalyst machine.
    • Default DB name: macaDB (see config/settings.py).
    • Contains relevant time-series metrics for the analysis time window.
  • JMeter Results
    • Aggregate and summary result files from your JMeter test run.
    • Placed under:
      • JMeterResults/aggregate/
      • JMeterResults/summary/
    • Filenames/formats must match expectations in data_sources/jmeter_reader.py.
  • Other Metrics (Apache, Tomcat, Oracle, OS)
    • Metrics available as required by:
      • data_sources/apache_reader.py
      • data_sources/tomcat_reader.py
      • data_sources/oracle_reader.py
      • data_sources/os_loader.py
    • These may read from InfluxDB, logs, or other data stores depending on implementation.

2. Configuration

2.1 Global Settings (config/settings.py)

Important configuration values:

  • InfluxDB Connection
    • INFLUX_HOST = "localhost"
    • INFLUX_PORT = 8086
    • INFLUX_USERNAME = "admin"
    • INFLUX_PASSWORD = "admin"
    • INFLUX_DB = "macaDB"
  • Time Window
    • START_TIME = "2026-05-29T08:36:20Z"
    • END_TIME = "2026-05-29T11:18:52Z"
    • Must align with both InfluxDB metrics and JMeter test period.
  • Thresholds (partial list):
    • CPU / Memory:
      • CPU_HIGH_THRESHOLD = 85
      • MEMORY_HIGH_THRESHOLD = 80
    • Latency / Error:
      • LATENCY_HIGH_THRESHOLD = 1000
      • LATENCY_CRITICAL = 1500
      • ERROR_RATE_THRESHOLD = 0.05
      • ERROR_CRITICAL_THRESHOLD = 0.1
    • Correlation & anomaly behavior:
      • CORRELATION_THRESHOLD
      • CPU_RT_CORR_THRESHOLD
      • MEMORY_LATENCY_CORR_THRESHOLD
      • MIN_SUSTAINED_DURATION, MIN_DURATION, TREND_THRESHOLD, ANOMALIES_THRESHOLD
    • Component-specific thresholds:
      • Apache: latency, error rate, worker utilization.
      • Tomcat: GC time/count, heap usage, threads, DB connections.
      • Oracle: exec time, wait time, calls, memory.
  • JMeter results path
    • JMeterResultPath = Path("JMeterResults/aggregate/")

Adjust these values to match your environment (non-localhost InfluxDB, different DB name, different JMeter directories, custom thresholds).

2.2 Monitoring Configuration (config/monitoring_config.yaml)

This YAML file is loaded by:

config = ConfigManager("config/monitoring_config.yaml")

It typically defines:

  • Which servers/hosts are monitored.
  • Which metrics to pull for each component (CPU, memory, Apache, Tomcat, Oracle, OS).
  • Any per-metric or per-source configuration.

Before running:

  1. Open config/monitoring_config.yaml.
  2. Verify hostnames, measurement names, and other settings match your environment.
  3. Save your changes.

3. Running the Application

3.1 From Command Line

  1. Open a terminal / command prompt.
  2. Navigate to the project root: 
    cd "c:\Nikhil P\SVN\Asset\13_PerformanceAnalyst\PerformanceAnalyst"
  3. Activate your Python environment (if using virtualenv/conda).
  4. Run the main script: 
    python Main.py
  5. The application will:
    1. Load configuration from config/monitoring_config.yaml via ConfigManager.
    2. Load metrics from configured data sources via dataLoader(config).
    3. Aggregate metrics with aggregate_all(metrics_collection, config).
    4. Perform anomaly and pattern/correlation analysis using detect_anomalies_and_patterns(aggregated_data).
    5. Run the rule engine (run_rule_engine_with_output) to produce final_results.
    6. Print a short summary to the console via print_short_output(final_results).
    7. Persist detailed outputs and an HTML report via save_detailed_output(final_results) and generate_html_report(final_results).

3.2 Console Output

Main.py calls:

print_short_output(final_results)

For each flow, this prints:

  • Major bottlenecks (HIGH severity issues).
  • Risks (MEDIUM severity issues).
  • Top action items / recommendations (up to a few items).
  • Overall confidence in the analysis, with guidance on interpretation.

Additional, more verbose helper functions defined in Main.py:

  • print_sample_data(metrics_collection, rows=5) – prints sample JMeter and per-server metrics.
  • print_actionable_output(final_results) – detailed, flow-centric view with summaries, chains, layer breakdown, evidence, and recommendations.

These helpers are currently commented out in the main block. You can enable them if you want richer CLI output while debugging or exploring data.

4. Outputs

4.1 File Outputs

Within Main.py:

save_detailed_output(final_results)
generate_html_report(final_results)

These functions, implemented in utils/output_writer.py, will:

  • Write structured, detailed results (per flow and server) to files under the configured output directory (commonly output/).
  • Generate an HTML summary report that you can open in a browser.

Check the output/ directory (or the directory configured in output_writer.py) for:

  • JSON or similar structured exports.
  • HTML report(s) summarizing analysis, evidence, and recommendations.

5. Typical Run Checklist

5.1 Before Running

  • [ ] InfluxDB is running and reachable.
  • [ ] JMeter result files are present in:
    • JMeterResults/aggregate/
    • JMeterResults/summary/
  • [ ] config/settings.py:
    • [ ] Influx host/port/DB are correct.
    • [ ] START_TIME / END_TIME match your test window.
    • [ ] Thresholds are reasonable for your environment.
  • [ ] config/monitoring_config.yaml is aligned with your servers and metric naming.
  • [ ] Python dependencies are installed; the correct environment is active.

5.2 Running & Reviewing Results

  • [ ] Run python Main.py from the project root.
  • [ ] Review console output for:
    • Key bottlenecks.
    • Risks.
    • Action items.
    • Confidence level.
  • [ ] Open generated HTML report(s) and detailed outputs in the output/ directory.

6. Troubleshooting

6.1 No Data / Empty Analysis

  • Verify START_TIME / END_TIME in config/settings.py overlap with:
    • The JMeter test execution time.
    • Metric availability in InfluxDB.
  • Check hostnames and measurement names in:
    • config/monitoring_config.yaml
    • Data source readers (e.g., influx_reader.py, apache_reader.py).

6.2 InfluxDB Connection Errors

  • Confirm host/port/credentials in config/settings.py.
  • Ensure InfluxDB is running and accessible from this machine (network/firewall).
  • Verify the database INFLUX_DB exists and contains metrics.

6.3 JMeter Parsing Issues

  • Check that result files are in the expected directories:
    • JMeterResults/aggregate/
    • JMeterResults/summary/
  • Verify file formats (columns, delimiters) match what jmeter_reader.py expects.

6.4 Missing Apache / Tomcat / DB Metrics

  • Review:
    • data_sources/apache_reader.py
    • data_sources/tomcat_reader.py
    • data_sources/oracle_reader.py
    • data_sources/os_loader.py
    to understand how and where they look for data.
  • Ensure that:
    • Backing data sources (logs, Influx measurements, etc.) exist.
    • Names (measurements, fields, hostnames) are consistent with configuration.

For a deeper explanation of the analysis logic, refer to Docs/SystemDesign.html.
